## 写在前面

这篇文章是“非洲鸡的小窝”的第一篇正式技术文章，目前先以草稿形式保存，等我审核内容、补充细节之后再正式发布。

这是我个人搭建的第三个博客网站。前两个博客因为没有妥善管理，服务器实例的资源被释放，最终没能找回。经历过这件事之后，我痛定思痛，决定把这个博客放在相对稳定、可以长期保存的 GitHub 上，也借助 Git 的版本管理给内容多一层保障。

我一直想拥有一个真正属于自己的个人博客。它不需要承担复杂的业务，也不追求每天更新，只希望能留下技术实践、生活片段、阅读记录、项目复盘和一些还没有想透的个人思考。

所以，这个博客的定位很简单：做一块轻量、可持续维护、能够长期保存的个人数字空间。

## 整体方案

“非洲鸡的小窝”采用的是一套静态博客方案：

```text
Markdown 文章
      ↓
Hugo 静态构建
      ↓
GitHub Actions 自动部署
      ↓
GitHub Pages 发布
      ↓
https://seasealji.github.io/
```

写文章时，我只需要在项目中创建一个 Markdown 文件，补充标题、日期、分类和标签。Hugo 会读取这些内容，根据模板生成 HTML、RSS、站点地图和分类页面，最后由 GitHub Pages 提供访问。

这种方式没有数据库，也不需要单独维护服务器。文章本身就是文件，网站最终也是一组静态文件，结构清晰，迁移和备份都比较方便。

## 技术架构

### 1. Hugo：负责内容和页面生成

Hugo 是这个博客的核心构建工具。文章放在 `content/` 目录中，页面结构由 `layouts/` 目录中的模板决定，样式和交互分别由 CSS 和 JavaScript 负责。

目前主要的目录关系如下：

```text
content/              文章、关于页、分类页和音乐页
layouts/              Hugo 页面模板与可复用组件
static/css/           全站视觉样式
static/js/            深色模式、导航和音乐播放器交互
static/music/         随站点发布的本地音频文件
data/music.yaml       音乐播放列表和歌曲信息
archetypes/           新文章的默认 front matter 模板
hugo.toml             站点配置、菜单和分类设置
```

每篇文章使用 Hugo front matter，例如：

```toml
+++
title = "文章标题"
date = 2026-09-11T13:00:00+08:00
draft = true
categories = ["技术"]
tags = ["Hugo", "实践"]
+++
```

这里把 `categories` 用作较少的内容大类，把 `tags` 用作更具体的关键词。这样既能保持分类导航简洁，也方便之后按主题检索文章。

### 2. GitHub Pages：负责网站托管

博客部署在 GitHub Pages 上，仓库名称为 `SeaSealji.github.io`。这是 GitHub Pages 的用户站点形式，发布后可以通过个人域名直接访问。

静态站点部署到 GitHub Pages 有几个好处：配置简单、成本低、访问稳定，并且内容和代码都可以在 GitHub 中统一管理。

## 自动部署流程

每次向 `main` 分支推送代码后，GitHub Actions 会自动执行部署工作流：

1. 检出仓库代码；
2. 安装指定版本的 Hugo；
3. 配置 GitHub Pages；
4. 执行 `hugo --gc --minify` 构建网站；
5. 将生成的 `public/` 目录上传为部署制品；
6. 通过 GitHub Pages 发布到线上。

工作流文件位于 `.github/workflows/hugo.yaml`。这样以后写完文章，只需要提交并推送，剩下的构建和部署就交给 Actions 完成。

本地写作时，则可以使用：

```bash
hugo server -D
```

`-D` 会把草稿也显示出来，适合在发布前检查文章排版。正式发布前，将 front matter 中的 `draft = true` 改成 `draft = false` 即可。

## 音乐页面是怎么工作的

音乐页面使用“静态音频文件 + YAML 播放列表”的方式实现。

- 音频文件放在 `static/music/`；
- 歌曲标题、歌手和文件路径写在 `data/music.yaml`；
- Hugo 将它们渲染成播放列表；
- 浏览器通过静态资源地址流式播放音频。

播放器支持播放、暂停、上一首、下一首、进度拖动、音量调节和播放列表展开。页面不会自动播放，避免打开博客时突然发出声音。

由于音频文件会进入 Git 仓库，需要留意文件体积和版权问题。目前音乐文件使用批量脚本推送，推送成功后本地工作区不保留音频副本，同时通过 Git 的 `skip-worktree` 标记避免之后提交页面时误删远程音乐。

## 为什么选择这套方案

这套架构并不复杂，但和个人博客的需求比较匹配：

- **内容优先**：文章是普通 Markdown，不依赖后台管理系统；
- **维护成本低**：没有数据库、服务器和复杂运行环境；
- **版本清晰**：每次修改都能在 Git 中追踪；
- **发布自动化**：写完文章后推送即可触发部署；
- **扩展方便**：分类、标签、RSS、音乐页都可以继续用文件和模板扩展。

当然，它也有边界。比如它不适合复杂的用户系统、实时评论或高频动态数据。如果以后需要这些能力，可能要为博客增加独立服务；但对于现在的记录和分享需求，静态架构已经足够。
